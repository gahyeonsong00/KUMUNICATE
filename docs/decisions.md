# 결정사항 (2026-10-10 기준)

## 사용자와 로그인
- Google 로그인, `@khu.ac.kr` 계정만 허용. 국제캠퍼스 학부생·대학원생·교직원 모두 사용 가능 (팀 최종 확인 필요)
- 가입 시 받는 정보: 사용자 유형(학부생/대학원생/교직원), 소속(단과대·학과 또는 대학원, 교직원은 부서)
- 가입하면 모두 일반 사용자. `staff` 역할과 담당 부서는 **운영 계정(admin)이 대시보드 SQL로 지정** (Google 로그인만으로 학생/교직원 구분 불가)
- 학번은 받지 않는다. Google 로그인으로 받는 이름·학교 메일과 가입 시 소속으로 충분하다

## 교직원의 두 역할
- 계정은 하나. staff는 '민원 내기'와 '부서 민원함'을 전환해서 쓴다
- 교직원은 민원을 낼 때 부서를 직접 고를 수 있다 (AI 분류 생략)
- 자기 부서로 가는 민원도 막지 않는다

## 권한 (RLS)
- 민원인: 자기 민원만
- staff: 자기 민원 + **자기가 담당한 민원**의 내용. 부서 민원은 읽기 전용 요약(제목·담당자·상태·경과)만, **배정 전 민원은 내용 비공개**
- 답장·채팅·처리 완료·다른 부서로 넘기기는 **담당자만** 할 수 있다 (서버에서 막음)
- admin: 개발팀 운영 계정. 역할 지정·데이터 정정만 하고 민원 업무 권한은 없다 (10/10 변경)

## 민원 분류
- 라벨은 `data/labels/departments.csv`의 `code` (24개). 서버의 `departments` 테이블 seed로 사용
- `COLLEGE_OFFICE`, `GRAD_OFFICE`는 실제 행정실을 정하기 위해 `target_college`가 필요하다
  - 기준은 민원인 소속이 아니라 **문의 대상 수업·학과를 맡은 단과대**. 알 수 없으면 민원인 소속
- `UNASSIGNED`(미분류)는 별도 대기열. 직원이 다음 민원 받기를 누를 때 자기 부서 대기가 0건이면 미분류에서 받아 맞는 부서로 넘긴다
- **분류 규칙(프롬프트, 단서 우선순위, 애매한 경우 처리)은 분류 담당 팀원이 정한다.** 서버는 입력을 넘기고 결과를 저장만 한다
- 분류는 ChatKHU 사용 (대회 필수 조건)

## 분류 함수 입출력 (초안, 분류 담당과 합의 필요)

입력:
```json
{
  "complaint_id": "uuid",
  "content": "공학관 3층 화장실 변기가 막혔어요",
  "building_id": "engineering",
  "requester": { "type": "undergrad", "college": "software", "department": "인공지능학과" }
}
```

출력:
```json
{
  "department": "FACILITY_REPAIR",
  "target_college": null,
  "confidence": 0.92,
  "summary": "공학관 3층 화장실 변기 막힘"
}
```
`target_college`는 `COLLEGE_OFFICE`·`GRAD_OFFICE`일 때만 값이 있고 나머지는 null.

**(10/09 변경) 단과대는 이름이 아니라 `colleges` 테이블 code로 주고받는다.** 입력 `requester.college`와 출력 `target_college` 모두 해당.
한글 이름을 돌려주면 저장에 실패한다. 행정실인데 `target_college`를 모르면 null로 두면 서버가 민원인 소속으로 채운다.
입력 `building_id`는 `buildings.id`, 채팅 접수면 null. 분류 담당은 `supabase/functions/classify-complaint/classify.ts`만 채운다.

## 민원 처리 흐름
- 접수 경로 4가지: 챗봇 대화 후 접수, 챗봇 이관(챗봇이 답 못한 문의), 접수서 직접 작성, 꾸미기
- 꾸미기도 민원이다. 꾸미기 결과(전후 이미지)를 첨부해 담당 부서로 일반 민원처럼 전달
- 민원인 신원: **익명 없음** (10/10 변경, 악용 방지). 담당 직원에게 이름 / 학교 메일 / 소속을 보여준다
- 답하는 방법 두 가지
  - 채팅: 채팅으로 접수됐거나 담당자가 채팅을 시작한 민원. 대화가 끝나면 담당자가 '대화 종료 후 처리 완료'
  - 답변서: 공식 답변을 보내면서 처리 완료. 민원인 '나의 활동'에 공식 답변으로 표시
- 재문의: 처리 완료 후 **7일 안에만** 가능 (서버 함수가 확인). 새 민원이 아니라 **같은 민원 번호를 다시 열고**(재문의 표시) 같은 담당자에게 간다. 7일이 지나면 새 민원으로 접수
- 성장 게이지는 민원인 화면 몫 (직원 화면·서버 이번 범위 밖)

## 민원 배정과 상태 (2026-10-10, grill 방식으로 정함)
- **다음 민원 받기**: 직원이 목록에서 고르지 않는다. 버튼을 누르면 서버가 그 부서에서 **가장 오래 기다린 미배정 민원 1건**을 배정한다
  - 동시에 눌러도 서버가 한 번에 처리해 한 건씩 다른 민원을 준다 (중복 처리·헛수고 방지)
  - 자기 부서 대기가 없으면 미분류 대기열에서 받는다
  - 다른 부서에서 넘어오거나 되돌아온 민원은 **처음 접수 시각** 순서로 다시 줄을 선다
- **담당 해제**: 담당자 본인이 풀면 원래 순서대로 대기열에 돌아간다
- **자동 되돌리기**: 배정 후 영업일 2일(주말 제외, 공휴일은 계산 안 함) 동안 답장·채팅·처리가 없으면 담당을 풀고 대기열로 돌린다. 이력에 남기고 원래 담당자에게 알린다
- **다른 부서로 넘기기** (이관): 담당자가 허락 없이 직접 한다. 넘기면 담당자가 비고 받는 부서 대기열로 간다
  - 넘기는 이유 4개 중 필수 선택: 우리 부서 업무가 아님 / 다른 부서가 관리하는 시설 / 학사·장학 관련 문의 / 기타(덧붙일 말 필수)
  - 덧붙일 말은 선택. 이유는 **받는 부서 담당자와 분류 담당**만 본다 (민원인에게 비공개). 오분류 사례 데이터로도 쓴다
- **상태는 행동에 따라 자동으로 바뀐다** (직원이 상태 버튼으로 바꾸지 않음)

| DB 코드 | 담당자 | 직원 화면 | 민원인 화면 (팀원 구현) | 바뀌는 때 |
|---|---|---|---|---|
| `received` | 없음 | 배정 대기 | 접수 완료 → 배정 대기 | 민원 접수, 담당 해제, 넘기기, 자동 되돌리기 |
| `in_progress` | 있음 | 처리 중 | 배정 완료 · 처리 중 | 다음 민원 받기, 재문의 |
| `resolved` | 있음 | 처리 완료 | 처리 완료 | 답변서 전송, 채팅 종료 |

- DB 상태는 3단계 그대로. '접수 완료'와 '배정 대기'는 분류가 끝났는지로, '배정 대기'와 '처리 중'은 담당자 유무로 구분한다
- 지연: 접수 후 3일이 지났는데 처리 완료가 아닌 민원. 저장하지 않고 화면에서 계산
- 서버 구현 (10/10, `20261010000100_assignment_queue.sql`)
  - 미분류에서 받은 민원은 받은 직원의 부서 민원이 된다. 맞지 않으면 그 직원이 넘긴다
  - 자기가 낸 민원은 자기가 받지 않는다
  - 접수 시각은 서버가 정한다 (앱이 과거 시각을 보내 대기 순서를 앞당기는 것 방지)
  - 자동 되돌리기는 Supabase pg_cron이 30분마다 확인. '활동'은 담당자가 보낸 채팅·답변서
  - 민원인 본문 수정 잠금은 처음 배정된 순간부터 (해제돼 대기열에 돌아가도 다시 열리지 않음)

## 직원 화면 (2026-10-10)
- Vite + React + TypeScript, React Router. 직원 화면은 `/admin`, Carbon 디자인 시스템(`@carbon/react`), 크림슨 `#9E1B24` 단일 강조색, IBM Plex Sans KR
- **내 민원 탭**: 대기열 번호표(대기 N건, 가장 오래 기다린 시간, 다음 민원 받기) + 카드 3개(내가 처리 중 / 지연 / 오늘 처리 완료, 누르면 거르기) + 내가 맡은 민원 표(도착 순, 검색)
- **부서 현황 탭** (읽기 전용): 직원별 처리 중·지연·오늘 완료 건수 + 부서 민원 목록. 배정 전 민원은 '배정 전 (내용 비공개)'
- **민원 처리 화면**: 접수 경로에 따라 챗봇 기록·채팅·답변서·꾸미기 이미지가 자동으로 펼쳐진다. 구획 접기·폭 조절, 담당 해제, 다른 부서로 넘기기
- 만들지 않기로 한 것: 왼쪽 메뉴, 부서별 분류, 우선 처리 목록, 처리 상태 버튼, '지금 보고 있음' 표시, 직급(팀장) 역할
- 디자인 원본(`design/*.dc.html`)은 참고용으로 그대로 둔다. 원본의 익명 문구·시연용 사례 버튼·관리자 기능은 위 결정이 우선

## 서버 설계 결정 (2026-10-09, Claude Code와 grill 방식으로 질의응답하며 정함)
- 스키마는 `supabase/migrations/`에 기능별 SQL 파일로 둔다. 프론트 사용법은 `supabase/README.md`
- 가입 제한: Google `hd` 옵션 + DB 트리거로 @khu.ac.kr 강제. 심사위원용 데모 계정은 `allowed_emails` 예외 + 이메일/비밀번호
- 역할 지정은 관리자 화면 없이 대시보드 SQL로. 행정실 staff는 담당 단과대(`staff_college_code`)도 지정하고, 그 단과대 민원만 본다
- 행정실 배정은 단과대 단위까지만 (학과 사무실 단위 X)
- 직원도 민원은 민원인 화면에서 낸다. staff만 부서를 직접 고를 수 있고, 고르면 AI 분류를 건너뜀
- 건물: 공식 국제캠퍼스맵 33곳. 건물 하나에 단과대 여러 개 가능(`college_codes`). 지도 좌표는 지도 담당이 채움
- 첨부: 사진 최대 3장 + 문서(pdf·hwp·hwpx·docx) 최대 2개, 파일당 10MB. 동영상은 비용 때문에 제외. 본문 500byte
- 분류 호출: 앱이 저장 후 `classify-complaint`에 `complaint_id`만 넘김. 실패해도 민원은 접수됨
- 수정: 민원인은 담당자가 받기 전(담당자 없음)만 수정 가능, 이후는 채팅으로 요청. 삭제 없음
- 미분류(`UNASSIGNED`·분류 실패)는 미분류 대기열로 (위 '민원 배정과 상태'). 시연용 직원 계정은 **관리팀 일반 staff** (10/10 변경, 이전: admin)
- 상태는 DB에 `received`/`in_progress`/`resolved` 영문 코드로 저장
- 직원 내부 메모는 민원인이 못 보게 별도 테이블(`complaint_notes`)로 분리
- 재배정(넘기기)은 `reassign_complaint` 함수로만 (Postgres는 바뀐 행도 조회 권한을 다시 확인하기 때문에 직접 update로 남의 부서에 넘기면 막힘. 점검 스크립트로 발견)
- 권한 규칙은 `supabase/tests/rls-check.mjs`로 자동 점검 (PGlite로 로컬에서 실제 Postgres 실행)
