# 꾸미기 모드 AI 설계 (확정본 v4, 2026-10-10)

사용자가 꾸미기 모드에서 지도의 한 지점을 고르고 "분수 주변에 벤치 놔줘"라고 입력하면,
그 주변 지도를 나노바나나가 고쳐 그려서 같은 자리에 겹쳐 보여주는 기능.
사람마다 자기 지도를 가진다: **원본 지도 + 내가 저장한 꾸미기 조각들 = 내 지도**. 원본은 절대 바뀌지 않는다.

> 팀 앱 **KUMUNICATE**(gahyeonsong00/KUMUNICATE)에 넣는다. 화면은 친구 설계도 `design/Decorate.dc.html` 모양 그대로,
> 서버는 친구 Supabase에 합친다. 넣는 방법은 아래 **8절**.

> 지도 제작 쪽 결정은 `../docs/decisions.md`를 따른다 (v4 원본, 3×3 칸, Leaflet).
> decisions.md의 "범위 밖: 꾸미기 저장"은 **지도 제작 작업의 범위**를 말한 것이고,
> 꾸미기 모드는 이 폴더의 별도 작업으로 진행한다.

## 1. 확정된 결정

| # | 항목 | 결정 |
|---|---|---|
| 1 | 방식 | 선택 지점 주변만 잘라 **나노바나나로 이미지 편집**. 전체 지도·원본 이미지는 절대 수정하지 않음 |
| 2 | 서버 | **Supabase Edge Function**. 키는 서버 비밀값(환경변수)에만 |
| 3 | 키·크레딧 | **ChatKHU API Gateway 키 하나**로 Claude와 나노바나나 모두 호출. 꾸미기 담당 계정 키를 `DECORATE_CHATKHU_API_KEY`로 따로 등록 (민원 분류·채팅의 `CHATKHU_API_KEY`와 크레딧 분리) |
| 4 | 시연 장소 | **사색의 광장** (v4의 **4번 칸**, 기준 칸이라 가장 먼저 완성됨). 르네상스공원(3번 칸)은 완성 후 추가 |
| 5 | 자르는 크기 | **최종 고화질 지도 기준 1024×1024 고정** (v4 원본 기준 약 256px, 건물 하나 + 주변). 누른 지점이 가운데, 지도 가장자리에서는 안쪽으로 밀어서 자름 |
| 6 | 결과 표시 | **내 지도의 같은 자리에 겹치기** (Leaflet `imageOverlay`, 잘라낸 영역과 같은 bounds). 결과의 가운데 80%를 쓰고 바깥 테두리는 아래 지도와 부드럽게 섞음 (CSS mask). 꾸미기 화면에서는 바뀐 부분을 사진 상자 비율(약 1.68:1)로 잘라 **팝업**으로 꾸미기 전/꾸민 후 탭 표시 |
| 7 | 바탕 그림·수정하기 | 새 꾸미기는 **시작할 때의 내 지도**(원본 + 저장한 꾸미기)에서 잘라 그림. 수정하기는 직전 결과가 아니라 **그 시작 바탕에서 다시** 그림. Claude가 이전 요청까지 합쳐 하나의 최종 변경 내용으로 정리. 저장 안 한 결과는 바탕에 안 들어감 |
| 8 | Claude 역할 | 요청 판단(edit / question / not_visual / reject) + 나노바나나 프롬프트 빈칸 채우기 + 말풍선 문장 + 담당자용 요약 |
| 9 | 나노바나나 모델 | **일반 모델**로 시작. 화풍이 깨지면 환경변수 하나로 Pro로 교체 |
| 10 | Claude 입력 | 사용자 문장 + **잘라낸 이미지(내 지도 기준)** + 장소 이름 + 이번 세션의 이전 요청들 |
| 11 | 저장 | 결과 그림, 꾸미기 전 조각, 위치(지도 좌표), 원문, 최종 프롬프트, 담당자용 요약 저장. **저장**은 내 지도·히스토리에만. 저장 안 하고 화면을 나가면 사라짐. 수정을 여러 번 했으면 마지막 것 하나만 저장. **제안하기 버튼은 나중에 추가** (그때 담당자 전달) |
| 12 | 제한 | 사용자당 **하루 5회** (이미지 생성이 일어난 요청만 셈). 실패하거나 30초가 넘으면 "다시 시도". 시연 계정(친구 서버 `allowed_emails`의 데모 계정)은 무제한. 키 계정의 **남은 크레딧이 기준(기본 500) 아래면 시연 계정 외 생성 중단** (월 4,000크레딧 ≈ 50여 장) |
| 13 | 장소 | **33곳** (`app/public/features/campus-data.js` = 친구 서버 `buildings` 테이블, 번호 `map_no`가 같음). 꾸미기 위치는 **메인에서 고른 장소의 좌표**를 가운데로 씀. (좌표는 decisions.md대로 v4에 다시 맞춘 값) |
| 14 | 프롬프트 틀 | 검증된 B 단계 틀을 **서버에 고정**. Claude는 빈칸만 채움. 한국어 |
| 15 | 원본 지도 | **완성 지도 `art/map_final.png`**(6028×4176 = v4 × 4, 2026-10-11). 서버에는 1024 조각 30개(`decorate-maps/final/r{행}_c{열}.png`)로 두고 핀 주변 조각만 이어 붙임(한 장을 통째로 열면 무료 서버 CPU 제한). 33곳 전부 꾸밀 수 있음. 꾸미기마다 어느 지도에서 만들었는지(`map_id`) 기록하고, 지도가 바뀌면 예전 지도의 꾸미기는 내 지도에 겹치지 않음. (완성 전에는 4번 칸 4배 확대 임시 그림 `tile04`로 개발) |
| 16 | 히스토리 삭제 | **최신 것부터만** 삭제 가능 (맨 위 항목만 버튼 켜짐, 나머지는 "최근 꾸미기부터 지울 수 있어요"). 누르면 그 꾸미기 하나만 원본으로. 기록은 서버에 남김 |
| 17 | 초기화 | 내 지도 전체를 원본으로 (내 꾸미기 전부 숨김). 기록은 서버에 남김 |
| 18 | 꾸미기 보기 스위치 | 메인 지도에서 **켜면 내 지도, 끄면 원본 지도**. 다른 사람 꾸미기는 안 보임 |
| 19 | 말풍선 | Claude 답(결과 설명·질문·민원 안내·거절·한도 초과·다시 시도)은 **쿠밍이 대화창**(메인 설계도 모양)에, 사진 상자와 입력창 사이 |
| 20 | 로딩 | 설계도의 쿠밍이 "경희대를 꾸미는중..." |
| 21 | 되돌리기 | **없음** (꾸미기 전 탭 + 수정하기로 대신) |

## 2. 처리 흐름

```
[화면] 메인 지도에서 장소 선택 → 꾸미기 화면 → "이 자리를 어떻게 바꾸고 싶나요?" 입력 → AI로 생성하기
   │  보내는 것: 장소 id(좌표는 서버가 장소에서 정함), 사용자 문장, 세션 id, 이번 세션 이전 요청 id
   ▼
[서버: Edge Function]
 1) 오늘 사용 횟수 확인 (5회 초과면 거절 + 안내 문장), 남은 크레딧 확인
 2) 원본 지도 + 이 사용자가 저장한 꾸미기를 겹친 "내 지도"에서 (x, y) 중심 1024×1024 잘라내기
    (화면과 같은 방식으로 테두리를 섞어서 겹침. 같은 세션의 수정하기는 이 바탕을 다시 씀)
 3) Claude 호출: 시스템 프롬프트 + 잘라낸 이미지 + 장소 이름 + 이전 요청들 + 이번 문장
    → JSON 검사 (형식이 틀리면 1회 재시도, 그래도 틀리면 실패 처리)
 4) type이 edit가 아니면 → reply만 돌려주고 끝 (이미지 생성 안 함, 횟수도 안 셈)
 5) edit이면 → 서버의 고정 틀에 Claude의 빈칸을 채워 나노바나나 프롬프트 완성
 6) 나노바나나 호출: 이미지 1 = 잘라낸 그림, 프롬프트 = 5)의 결과
 7) 결과를 1024×1024로 맞추고 Storage에 저장(꾸미기 전 조각도 함께), DB에 기록, 횟수 +1
   ▼
[화면] 쿠밍이 로딩 → 내 지도 같은 자리에 겹쳐 표시 (테두리 부드럽게)
       → 팝업 사진 상자에 꾸미기 전/꾸민 후 탭, 쿠밍이 대화창에 reply
       → 저장 / 수정하기(이어서 입력). 히스토리 삭제(최신부터) / 초기화. 제안하기는 나중에
```

## 3. Claude 시스템 프롬프트

`{{ }}`는 서버가 채운다. 잘라낸 이미지는 메시지에 이미지로 첨부한다.

```
너는 대학 캠퍼스 개선 제안 앱 "경희대 키우기"의 꾸미기 도우미야.
사용자는 캠퍼스 지도의 한 지점을 골라서, 그곳을 어떻게 바꾸고 싶은지 말해.
첨부된 이미지는 사용자가 고른 지점을 가운데에 둔 지도 조각(1024×1024, 픽셀 아트)이야.
결과는 이 조각의 가운데 가로 띠(위아래 각각 약 5분의 1을 뺀 부분)만 사진으로 보여줘.
너는 요청을 판단하고, 이미지 편집 AI에게 넘길 변경 내용을 정리해.
그림은 네가 그리지 않아. 이미지 편집 AI가 그려.

## 지금 상황
- 고른 장소: {{place_name}}
- 이번 세션에서 앞서 한 요청들 (오래된 순): {{previous_requests}}
- 이번 요청: {{user_message}}

## 판단 규칙
1. 요청이 지도 위 물리적인 변화(시설물 추가·삭제·이동, 나무·화단·그늘 추가, 바닥이나 색 변경 등)로
   그릴 수 있으면 type은 "edit".
2. 무엇을 원하는지 전혀 알 수 없을 때만 type은 "question". 짧은 질문 하나만 해.
   개수나 정확한 위치처럼 네가 적당히 정할 수 있는 건 묻지 말고 정해.
   개수를 안 말하면: 벤치·휴지통·자판기·그늘막은 2개, 가로등·나무·화단은 3개.
3. 운영 시간, 소음, 청소, 수업처럼 그림으로 보여줄 수 없는 요청이면 type은 "not_visual".
   reply로 민원 접수를 안내해. 안내할 곳은 "학교 민원 창구"라고만 하고, 부서나 게시판 이름을 지어내지 마.
4. 장난, 욕설, 특정인 비방, 선정적이거나 폭력적인 그림, 캠퍼스와 무관한 그림 요청이면 type은 "reject".
   reply는 정중하게 짧게. 요청에 이런 요소가 있으면 그 요소를 빼거나 바꿔서 그리지 말고 reject로 해.
5. 이번 요청이 앞선 요청을 이어받는 말("하나 더", "왼쪽으로", "아까 거 빼줘")이면,
   앞선 요청들과 합쳐서 **최종 상태 하나**로 정리해. 그림은 매번 첨부된 이미지에서 새로 그려지기 때문이야.
   예: "벤치 2개" 다음 "하나 더" → "벤치 3개".
   첨부된 이미지는 이번 꾸미기를 시작할 때의 지도라서, 앞선 요청들의 결과는 이미지에 없어.
   앞선 요청에서 만든 것을 "기존 ○○"라고 부르거나 "○○를 지운다"고 쓰지 말고, 이미지에 더할 최종 상태만 적어.
6. 변경은 이미지 **가운데의 가로로 긴 영역** 안에서 일어나게 위치를 정해. 위아래 각각 5분의 1과
   좌우 가장자리 근처는 피해. 이미지를 보고 실제로 빈 공간, 길, 잔디 같은 구체적인 자리를 골라.
   위치는 픽셀 숫자 없이 모양·방향으로 말해. 사용자가 말한 대상이 가장자리 쪽에 있으면
   그 대상의 가운데 쪽 면을 골라.
7. 새로 놓는 물체는 주변의 벤치·가로등·나무와 비슷한 크기여야 해.
8. 건물 철거나 교체처럼 큰 변화도 제안으로는 허용해. 단, 이미지 가운데에 들어오는 범위만.
9. 실제 설치 여부는 학교 담당자가 결정해. 사용자에게 "설치됩니다" 같은 약속은 하지 마.

## 출력 (이 JSON 하나만 출력해. 다른 글, 코드블록 표시는 쓰지 마)
{
  "type": "edit" | "question" | "not_visual" | "reject",
  "reply": "사용자 말풍선에 보일 한국어 존댓말 1~2문장",
  "change": "최종적으로 바뀔 내용 한 문장 (edit일 때만, 아니면 빈 문자열)",
  "location": "이미지 안에서 바뀔 위치를 모양·방향으로 1~2문장 (edit일 때만)",
  "details": ["물체의 모양, 색, 재질, 개수, 방향 등 그릴 때 필요한 세부사항 2~5개, 항목마다 한 줄로 짧게 (edit일 때만)"],
  "summary": "담당자용 한 문장: [장소] [무엇을 어떻게] 제안 (edit, not_visual일 때. question, reject면 빈 문자열)"
}
```

## 4. 나노바나나 프롬프트 틀 (서버에 고정)

```
이미지 1은 대학 캠퍼스 지도의 일부야. 아래 변경을 이미지 1의 가운데 부분에만 반영해줘.

[변경 내용]
{{change}}

[위치]
{{location}}

[세부]
{{details를 "- " 목록으로}}

[반드시 지킬 것]
- 시점, 크기 비율, 픽셀 아트 화풍, 색감, 그림자 방향은 이미지 1 그대로 유지해.
- 변경하는 부분 말고 다른 건물, 도로, 나무, 가장자리는 하나도 바꾸지 마.
- 새로 그리는 물체는 주변의 벤치, 가로등, 나무와 같은 크기 비율로.
- 글자, 숫자, 간판, 사람, 워터마크는 넣지 마.
- 이미지 1과 같은 크기, 같은 비율로 출력해.
```

## 5. 테스트 문장 (기대 결과)

시스템 프롬프트를 고칠 때마다 이 표로 다시 확인하고 `prompt-test-log.md`에 기록한다 (대회 평가 자료).

| 장소 | 이전 요청 | 이번 입력 | 기대 |
|---|---|---|---|
| 사색의 광장 | - | 연못 주변에 벤치 놔주세요 | edit, 벤치 2개, 연못 둘레 빈 바닥 |
| 사색의 광장 | 벤치 놔주세요 | 하나 더 | edit, change = 벤치 3개 |
| 사색의 광장 | 벤치 2개 | 아까 거 빼고 그늘막으로 | edit, change = 그늘막 2개 (벤치 없음) |
| 학생회관 | - | 앞에 그늘이 없어서 여름에 너무 더워요 | edit, 나무 또는 그늘막, reply로 설명 |
| 국제학관 | - | 밤에 이 길이 너무 어두워요 | edit, 가로등 3개 |
| 중앙도서관(대학본부) | - | 엘리베이터 고장났어요 | not_visual, 민원 안내 |
| 아무 곳 | - | 도서관 운영시간 늘려주세요 | not_visual |
| 아무 곳 | - | 음 | question |
| 아무 곳 | - | (욕설 / 선정적 그림 요청) | reject |

## 6. ChatKHU API Gateway 연결 정보

**나노바나나 편집 호출 형식** — OpenAI 호환 `chat/completions`·`images/edits`가 **아님** (둘 다 404).
게이트웨이 전용 엔드포인트를 쓴다.

```
POST https://factchat-cloud.mindlogic.ai/v1/gateway/images/generate/
Authorization: Bearer <키>
{
  "model": "gemini-3.1-flash-image-preview",
  "prompt": "...",
  "number_of_images": 1,
  "image_size": "1K",            // 0.5K | 1K | 2K | 4K (Pro는 1K부터)
  "aspect_ratio": "1:1",
  "input_images": ["data:image/png;base64,..."]   // data URL 그대로 받음 (공개 URL 불필요)
}
```

**응답 형식** (Google 모델은 동기 응답, 기다리면 바로 옴)

```
{ "id": "img-...", "model": "...", "created": ...,
  "data": [ { "url": "data:image/jpeg;base64,..." } ],
  "credits_charged": 69 }
```

- 결과는 **JPEG 1024×1024** (1K, 1:1) → 서버에서 PNG 변환 없이 그대로 저장해도 됨
- **워터마크: 없음** (오른쪽 아래 반짝이 없음 확인. 보이지 않는 SynthID만 있을 것) → `remove_sparkle.py` 불필요
- **걸린 시간: 11.0초** (1회). 30초 제한 안쪽
- **크레딧: 69 차감** (`credits_charged`로 응답에 옴). Claude는 `/claude/v1/messages` 그대로 (Anthropic SDK `baseURL`만 바꾸면 됨)
- 크레딧 확인: `GET /v1/gateway/credits/` (잔액), `GET /v1/gateway/usage/` (모델별 사용량). 가격 미리보기: `POST /v1/gateway/estimate/`
- 키 계정의 월 할당: **4,000 크레딧** (매월 1일 갱신). 일반 모델 기준 **한 달 약 57장**, Pro 약 28장
- 주의: `POST /v1/gateway/keys/revoke/` 는 **현재 키를 비활성화**하는 엔드포인트. 절대 호출하지 말 것
